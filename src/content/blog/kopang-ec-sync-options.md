[앞 글](/blog/kopang-redis-lua-stock/)에서 코팡의 재고 차감을 Redis Lua 스크립트로 옮겼습니다.
요청 흐름에서 DB가 하는 일은 주문 INSERT 하나만 남겼고, DB의 재고 숫자는 나중에 맞추기로 했습니다.

이 글은 그 "나중에 맞추기"를 어떤 방식으로 할지 비교한 기록입니다. 2026-01-02에 이슈 [#31](https://github.com/kodesalon/kopang/issues/31)을 열고 정리했습니다.
이 단계는 설계만 했고 코드는 없습니다. 이후 메시지 큐를 고르는 과정은 [다음 글](/blog/kopang-ec-mq-choice/)에 이어집니다.

## 무엇이 어긋나는가

2025-12-28 이후 주문 한 건이 처리되는 순서는 이렇습니다([2d4c592](https://github.com/kodesalon/kopang/commit/2d4c592)).

1. Redis에서 Lua 스크립트로 재고를 줄인다.
2. DB 트랜잭션에서 주문을 INSERT한다.
3. 주문 INSERT가 실패하면 Redis 재고를 되돌린다.

DB의 `stock.quantity`는 이 흐름 어디에서도 바뀌지 않습니다. 1,000개가 팔려도 DB에는 처음 넣은 1,000이 그대로 남습니다.
판매 수를 제한하는 기준은 Redis가 맡고 있으니 주문 처리 자체에는 문제가 없습니다. 하지만 운영 화면이나 Redis 장애 뒤 복구처럼 DB 재고를 보는 기능이 생기면, 그 기능은 틀린 숫자를 보게 됩니다.

## 비교 기준

방식을 고를 때 세 가지를 봤습니다.

- 효율: DB에 불필요한 쓰기를 얼마나 줄일 수 있는가
- 안전: 서버나 Redis에 장애가 나도 재고 변동 기록이 사라지지 않는가
- 복구: 숫자가 틀어졌을 때 얼마나 빠르고 정확하게 되돌릴 수 있는가

## 세 가지 방식

### 1. 품절 시점 동기화

Redis 재고가 0이 되는 순간 이벤트를 내서 DB 재고를 0으로 바꾸는 방식입니다.

- 효율: 재고가 몇 개든 DB 쓰기는 한 번입니다.
- 안전: 중간 저장이 없습니다. 99개가 팔린 뒤 서버가 죽으면, DB 재고는 여전히 처음 값입니다.
- 복구: 주문 테이블 전체를 세어 다시 계산해야 합니다. 주문이 많을수록 무겁습니다.

### 2. 주기 동기화

스케줄러가 짧은 주기(예: 10초, 1분)마다 Redis의 현재 값을 DB에 덮어쓰는 방식입니다.

- 효율: 주기마다 쿼리 한 번이라 DB 부하는 거의 없습니다.
- 안전: 서버가 죽어도 마지막 동기화 이후의 차이만 남습니다.
- 복구: 마지막 동기화 시각 이후의 주문만 범위로 조회하면 되므로 1번보다 가볍습니다.

### 3. 메시지 큐

재고가 바뀔 때마다 이벤트를 메시지 브로커에 발행하고, 별도의 소비자(consumer)가 이를 읽어 DB에 반영하는 방식입니다.

- 효율: 소비자가 DB가 감당할 수 있는 속도로 가져가므로 DB 부하가 일정합니다. 수백 건씩 묶어서 한 번에 반영할 수도 있습니다.
- 안전: 브로커가 메시지를 디스크에 저장하면 소비자나 DB가 멈춰도 메시지는 남습니다.
- 복구: DB가 오래 멈췄다가 돌아와도 쌓인 메시지를 차례로 처리하면 됩니다.

대신 두 가지 부담이 있습니다. 하나는 Redis 차감은 성공했는데 메시지 발행이 실패하는 경우를 따로 막아야 한다는 점입니다. 다른 하나는 브로커를 운영하는 비용입니다.

| 기준 | 품절 시점 동기화 | 주기 동기화 | 메시지 큐 |
| --- | --- | --- | --- |
| DB 쓰기 | 1회 | 주기마다 1회 | 변동마다(묶어서 처리 가능) |
| 장애 시 남는 차이 | 품절 전까지 전부 | 마지막 주기 이후 | 발행에 성공한 것은 보존 |
| 복구 | 주문 전체 집계 | 마지막 동기화 이후 범위 조회 | 쌓인 메시지 재처리 |
| 추가 부담 | 없음 | 없음 | 발행 실패 처리, 브로커 운영 |

## 결정

당시에는 이 프로젝트의 목표를 구현 편의보다 대규모 트래픽에서 생기는 문제를 확실히 푸는 쪽에 두었습니다.
그래서 품절 시점 동기화나 주기 동기화 대신 메시지 큐로 방향을 정했습니다. 어떤 브로커를 쓸지는 다음 단계로 넘겼습니다.

## 다시 보니 빠진 것

이번에 코드와 함께 다시 읽어 보니 비교에서 빠진 전제가 두 가지 있었습니다.

첫째, 주문은 이미 DB에 동기로 저장되고 있었습니다. 주문 INSERT가 실패하면 Redis 재고를 되돌리므로, 정상 흐름에서는 팔린 수량만큼 주문 행이 남습니다. 그렇다면 DB의 재고 숫자는 "처음 재고 − 유효한 주문 수량 합"으로 언제든 다시 계산할 수 있는 값입니다.
(Redis 차감 뒤 커밋 전에 프로세스가 죽는 경우는 예외입니다. 이때는 Redis 재고만 줄고 주문 행은 남지 않습니다.)
그렇다면 장애가 나도 잃지 말아야 할 기록은 주문 행이고, 그 행은 이미 DB 트랜잭션으로 지켜지고 있었습니다.
세 방식은 사실 "파생값인 재고 숫자를 얼마나 자주, 얼마나 싸게 갱신하는가"의 차이였습니다. 당시 표의 "안전" 칸은 이 점을 반영하지 못하고 세 방식의 위험을 실제보다 크게 적었습니다.

둘째, 재고는 줄기만 하지 않습니다. 결제 기한이 지난 주문이 취소되면 Redis 재고가 다시 늘어납니다. 품절 시점 동기화는 재고가 0이 된 뒤 다시 늘어나는 경우를 놓치고, 메시지 큐도 차감 이벤트만 보내면 DB가 계속 적게 셉니다.
이 문제는 최종 구현에서도 그대로 남았습니다. Outbox에는 차감(`DECREASE`) 이벤트만 기록되고, 취소로 재고를 되돌릴 때는 이벤트를 남기지 않습니다. [마지막 글](/blog/kopang-transactional-outbox/)에서 다시 다룹니다.

## 다시 확인한 것

| 당시 주장 | 확인 결과 | 근거 |
| --- | --- | --- |
| 재고 관리를 Redis로 옮겨 DB와 불일치가 생김 | 맞음. 요청 흐름에서 DB 재고는 갱신되지 않음 | [2d4c592](https://github.com/kodesalon/kopang/commit/2d4c592), 현재 `PurchaseOrchestrator` |
| 품절 시점 동기화는 서버가 죽으면 판매 내역이 증발 | 표현 수정. 주문 행은 DB에 남고, 사라지는 것은 DB의 재고 숫자 | `OrderService.createOrderPending`이 요청 중 동기 INSERT |
| 메시지 큐는 디스크 저장으로 유실이 없음 | 브로커 설정에 따라 다름. 발행 전 실패는 별도 대책 필요 | 원문도 단점으로 언급 |
| 메시지 큐로 방향 결정 | 맞음. 이 시점에는 설계만 있고 코드는 없음 | 이슈 #31 본문(2026-01-02) |
| 재고 복구(취소) 이벤트 | 비교에서 빠져 있었고 최종 코드에도 없음 | `OrderStockEventListener`가 `DECREASE`만 기록 |
