[2차 테스트](/blog/kopang-perf-phase2-cache/)를 마치고 스레드 덤프를 뜨려고 같은 테스트를 한 번 더 돌렸습니다. 코드도 설정(Tomcat 100 / Hikari 30)도 그대로였는데 결과가 크게 달랐습니다.

| 지표 | 첫 실행 (Cold) | 두 번째 실행 (Warm) |
| --- | --- | --- |
| 처리량 | 221.1 TPS | 882.2 TPS |
| p95 | 2.21초 | 341ms |
| 앱 서버 CPU (당시 비교표 값) | 32% | 85% |
| Load Average 최대 (2 vCPU) | 5.4 | 12.5 |

첫 실행의 CPU 32%는 당시 비교표에 적은 값이고 최대값은 아닙니다. 같은 실행의 모니터링 기록에는 시작 직후 93%까지 올랐다가 부하 유지 구간에서 30%대로 내려왔다고 되어 있습니다.

이 글은 이 4배가 어디서 왔는지 확인한 과정입니다. 근거는 당시 k6 출력, Grafana 지표, JIT 컴파일 로그, 커밋입니다. 테스트는 다시 돌리지 않았고, 로컬 JDK 21에서 컴파일 임계값 플래그만 다시 확인했습니다.

## 가설 두 개

같은 코드가 두 번째에 더 빨라질 이유로 두 가지를 떠올렸습니다.

1. 캐시 적중. 첫 실행은 캐시가 비어 있어 DB 조회가 일어나고, 두 번째 실행은 같은 스크립트가 같은 요청을 보내므로 거의 모두 캐시에서 나온다.
2. JVM 웜업. 첫 실행 동안 JVM이 자주 쓰이는 코드를 학습해 두 번째 실행에서는 최적화된 기계어로 돈다.

## 캐시 적중: 미스가 0이 됐다

Grafana의 Redis 적중·미스 지표를 두 실행에서 비교했습니다.

| 지표 | 첫 실행 | 두 번째 실행 |
| --- | --- | --- |
| 캐시 미스 | 초당 약 150 | 0 |
| 캐시 적중 | 거의 0 | 초당 2,100 이상 |

첫 실행에서는 초당 약 150번의 배송지 조회가 DB로 갔고, 두 번째 실행에서는 한 번도 가지 않았습니다.

여기에는 테스트 설계의 영향이 큽니다. k6 스크립트는 회원 번호 1~20,000을 돌려 가며 쓰고, 배송지 캐시의 TTL은 1시간입니다. 첫 실행은 2만 번 넘게 요청했으므로(221 TPS로 약 2분 50초) 회원 2만 명이 한 번씩은 거쳐 갑니다. 그 뒤 한 시간 안에 같은 테스트를 다시 돌리면, 두 번째 실행의 회원은 모두 이미 캐시에 올라가 있습니다.
실제 선착순에서는 한 사람이 보통 한 번 주문하므로, 이런 적중률은 나오기 어렵습니다. 이 점은 [Cache Warm-Up 글](/blog/kopang-cache-warmup-strategy/)에서 다시 다룹니다.

## JIT: 두 번째 실행에서만 C2까지 갔다

캐시만으로 4배가 설명되지 않는다고 봤습니다. 데이터가 빨리 와도 처리하는 코드가 느리면 한계가 있기 때문입니다. 그래서 JVM 웜업을 봤습니다.

먼저 클래스 로딩은 원인에서 뺐습니다. 부하 테스트에는 처음부터 30초짜리 웜업 시나리오(10 VU)가 있었고, 첫 실행에서도 이 시나리오가 돌았습니다.

다음은 JIT 컴파일입니다. HotSpot은 코드를 처음에는 인터프리터로 돌리다가, 자주 불리는 메서드를 단계별로 컴파일합니다.

| 단계 | 컴파일러 | 특징 |
| --- | --- | --- |
| Tier 0 | 인터프리터 | 바이트코드를 한 줄씩 실행 |
| Tier 1~3 | C1 | 빠르게 컴파일, 최적화는 제한적. Tier 3에서 프로파일 수집 |
| Tier 4 | C2 | 수집한 프로파일로 인라이닝 등 적극적 최적화 |

당시 참고 자료에는 "C2 임계값은 호출 1만 번"이라고 나와 있었고, 첫 실행에서 이미 약 3.7만 번 호출했으니 C2로 돌고 있었어야 했습니다. 그래서 JIT 가설이 틀렸나 싶었습니다.

실제로 C2가 돌았는지 보려고 배포 스크립트에 컴파일 로그 옵션을 넣었습니다([802c008](https://github.com/kodesalon/kopang/commit/802c008), 2026-02-01).

```bash
java -jar \
  -XX:+UnlockDiagnosticVMOptions \
  -XX:+PrintCompilation \
  -XX:+LogCompilation \
  -XX:LogFile=$JIT_LOG_NAME \
  ...
```

이 옵션은 2026-02-01에 들어갔으므로, 아래 로그는 01-30의 두 실행이 아니라 그 뒤 같은 조건으로 첫 실행과 두 번째 실행을 다시 돌려서 얻은 것입니다.
핵심 주문 메서드 `PurchaseOrchestrator::reserve`의 컴파일 기록은 이랬습니다(시각은 JVM 시작 후 ms).

```
291737   19814  !  2  ::reserve (177 bytes)
313917   21777  !  3  ::reserve (177 bytes)
313920   19814  !  2  ::reserve (177 bytes)   made not entrant
------------------------------------------------------------
2512682  28370  !  3  ::reserve (177 bytes)
2537131  31789  !  4  ::reserve (177 bytes)
2537268  28370  !  3  ::reserve (177 bytes)   made not entrant
```

- 첫 실행: 약 291초에 Tier 2, 약 22초 뒤 Tier 3. 테스트가 끝날 때까지 Tier 4는 나오지 않았습니다. 첫 실행은 C1 수준으로 끝났습니다.
- 두 번째 실행: 시작 약 25초 만에 Tier 4(C2)로 컴파일됐습니다.

## 1만 번을 넘었는데 왜 C2가 아니었나

이번에 JDK 21의 기본 플래그를 확인해 보니, 당시 참고한 "1만 번"은 단계별 컴파일을 끈 경우의 값(`CompileThreshold=10000`)이었습니다. 기본 설정에서 Tier 4로 가는 기준은 따로 있습니다.

```
$ java -XX:+UnlockDiagnosticVMOptions -XX:+PrintFlagsFinal -version | grep Tier4
     intx Tier4CompileThreshold      = 15000
     intx Tier4InvocationThreshold   = 5000
     intx Tier4LoadFeedback          = 3
     intx Tier4MinInvocationThreshold = 600
```

게다가 이 기준은 고정이 아닙니다. `Tier4LoadFeedback`은 C2 컴파일 큐가 길어질수록 기준을 올리는 값이고, 2 vCPU 서버에서는 C2 컴파일러 스레드도 적습니다.
앱이 막 떠서 컴파일할 메서드가 많이 쌓여 있는 첫 실행에서는 `reserve`가 C2 차례를 받지 못했을 가능성이 있습니다. 다만 컴파일 큐 길이를 기록하지 않아서 이것이 실제 원인인지는 확인하지 못했습니다.

## 두 원인을 나누지는 못했습니다

당시 결론은 "4배는 C2가 만든 기계어가 캐시 100% 적중 환경 위에서 돈 결과"였습니다. 두 현상이 모두 일어난 것은 로그로 확인됐습니다.
하지만 각각이 4배 중 얼마를 차지하는지는 재지 않았습니다. 나누려면 두 원인 중 하나만 바꾼 실행이 필요합니다.

- JVM만 새로 띄우고 Redis 캐시는 채워 둔 채로 실행 (캐시 적중, JIT 차가움)
- JVM은 그대로 두고 Redis 캐시만 비운 채로 실행 (캐시 미스, JIT 따뜻함)

이 실행은 하지 않았습니다.

## 이 결과가 이후 수치에 남긴 것

같은 코드와 설정에서도 첫 실행과 두 번째 실행이 4배 차이 난다는 것은, 성능 수치를 비교할 때 웜업 상태를 맞추지 않으면 비교가 성립하지 않는다는 뜻입니다.

[3차 테스트](/blog/kopang-perf-phase3-pool-ratio/)의 수치는 모두 두 번째 실행(Warm) 기준입니다. 반면 1차 테스트의 121.5 TPS는 첫 실행(Cold)이었습니다. 그래서 "1차 121 TPS에서 3차 466 TPS로 약 4배"라는 식으로 두 숫자를 나란히 놓으면, 이 글의 웜업 효과가 개선 효과에 섞여 들어갑니다. 3차 글에서 이 비교를 다시 정리했습니다.

## 남은 문제

882 TPS였지만 자원 상태는 좋지 않았습니다. Hikari는 active 30 / pending 69, JVM 스레드는 runnable 40 / timed-waiting 80이었습니다. Tomcat 스레드 100개 중 커넥션을 쥔 30개만 일하고 나머지 70개 가까이는 기다리는 상태였습니다.
여기서 Tomcat 스레드와 커넥션 수를 1:1로 맞춰 보자는 3차 테스트의 가설이 나왔습니다.

| 두 번째 실행은 캐시 미스 0 | 기록과 일치. 테스트가 회원 2만 명을 반복 사용한 영향이 큼 | Grafana 기록, `k6/performance-test.js` |
