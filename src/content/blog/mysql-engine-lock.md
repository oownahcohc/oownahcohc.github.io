이번 글에서는 MySQL에서 사용되는 잠금(Lock) 중에서 **MySQL 엔진 레벨의 잠금**에 대해 살펴보려고 한다.

MySQL 엔진 레벨의 잠금은 스토리지 엔진에 영향을 미치기 때문에, 각 잠금의 특징과 어느 시점에 사용되는지 알아둬야 한다.

지금부터 한번 살펴보도록 하자.

## 글로벌 락 (Global Lock)

> 💡 MySQL의 잠금 가운데 **범위가 가장 큰 잠금**이다.<br>
> **`FLUSH TABLES WITH READ LOCK`** 명령으로 획득할 수 있다.

글로벌 락은 MySQL 서버 전체에 영향을 미친다. 작업 대상 테이블이나 데이터베이스가 달라도 영향을 미친다는 뜻이다.

일단 하나의 세션에서 글로벌 락을 획득하면, 다른 세션에서 SELECT 를 제외한 대부분의 DDL 문장이나 DML 문장을 실행하는 경우 글로벌 락이 release 될 때까지 대기하게 된다.

MySQL 8.0 부터 InnoDB가 기본 스토리지 엔진으로 채택되어 트랜잭션을 사용하기 때문에, 일관된 데이터 상태를 위해 모든 데이터 변경 작업을 멈출 필요가 없어졌다. 즉, 글로벌 락 처럼 MySQL 서버 전체의 변경 작업을 멈추는 무거운 작업을 할 필요가 없어졌다는 것이다.

따라서 조금 더 **가벼운 글로벌 락**을 위한 <strong>백업 락(Backup Lock)</strong>이 도입되었다.

## 백업 락 (Backup Lock)

> 💡 백업 락은 **`LOCK INSTANCE FOR BACKUP`** 명령을 사용하여 획득할 수 있다.
>
> 이 명령은 백업 실행 전에 실행되며, 특정 세션에서 백업 락을 획득하면<br>
> **모든 세션에서 데이터베이스 및 테이블 등 모든 객체 생성 및 변경, 삭제가 불가능**해진다.
>
> 백업이 완료된 후에는 **`UNLOCK INSTANCE`** 명령을 사용하여 백업 락을 해제한다.

### 1. 테이블 스키마, 계정 관리 정보 변경의 차단

**LOCK INSTANCE FOR BACKUP** 명령을 통해 **백업 락을 획득**하면 모든 세션에서 다음과 같은 변경이 차단된다.

- 데이터베이스 및 테이블 등 모든 객체 생성 및 변경, 삭제 방지 (파일의 생성, 이름 변경 또는 제거를 방지)
- **REPAIR TABLE**, **TRUNCATE TABLE**, **OPTIMIZE TABLE** 명령 차단
- 계정 관리 및 비밀번호 변경 차단
- InnoDB redo 로그에 기록되지 않은 InnoDB 파일을 수정하는 작업 차단

### 2. 허용하는 변경은?

1. **일반적인 테이블 데이터 변경 허용**

   DML 의 허용 : **LOCK INSTANCE FOR BACKUP** 은 온라인 백업 중에 DML(INSERT, UPDATE, DELETE)을 허용하는 인스턴스 수준의 백업 락을 획득한다. 동시에 일관성 없는 스냅샷이 발생할 수 있는 작업을 방지한다.

2. **제한적인 DDL 작업 허용**

   사용자가 만든 임시 테이블에 대한 DDL : **LOCK INSTANCE FOR BACKUP** 은 사용자가 만든 임시 테이블에만 영향을 주는 DDL 작업을 허용한다. 실제로 백업 락이 유지되는 동안 사용자가 만든 임시 테이블에 속하는 파일은 생성, 이름 변경 또는 제거할 수 있다. 이진 로그 파일 생성도 허용된다.

### 3. 백업 락 실행 권한

**LOCK INSTANCE FOR BACKUP** 을 실행하려면 **BACKUP_ADMIN** 권한이 필요하다.

MySQL 8.0 버전 부터는 **RELOAD 권한을 가진 사용자에게 BACKUP_ADMIN 권한이 자동으로 부여**된다.

### 4. 백업 락 해제

**`UNLOCK INSTANCE`** 명령을 사용하면 현재 세션이 보유한 백업 잠금을 해제한다. 세션이 종료된 경우, 세션이 보유한 백업 잠금도 해제한다.

> 📌 **추가**
>
> MySQL 서버는 원본 데이터를 가진 <strong>소스 서버(Source Server)</strong>와 복제된 데이터를 가진 <strong>레플리카 서버(Replica Server)</strong>로 구성되고, **백업은 주로 레플리카 서버에서 실행**된다.
>
> **FLUSH TABLES WITH READ LOCK** 명령을 이용해 글로벌 락을 획득하면 복제는 백업 시간만큼 지연된다. 위에서 살펴봤듯이 해당 명령으로 글로벌 락을 획득하면 MySQL 서버의 모든 테이블에 대해 DDL, DML 을 수행할 수 없기 때문이다
>
> MySQL 서버의 **백업 락**은 **글로벌 락의 이런 문제를 해결하기 위해 도입**되었으며, 정상적으로 복제는 실행되지만 백업의 실패를 막기 위해 DDL 명령이 실행되면 **복제를 일시 중지하는 역할**을 한다.
>
> 예를 들어, 백업 락은 XtraBackup 이나 Enterprise Backup 툴이 실행되는 도중에 스키마 변경이 실행되면 백업이 실패하는 문제를 방지하기 위해 복제를 일시 중지시킨다.

## 테이블 락 (Table Lock)

> 💡 개별 테이블 단위로 설정되는 잠금

개별 테이블 단위로 잠금을 걸어주는 테이블 락은 **명시적** 혹은 **묵시적**으로 획득할 수 있다.

1. **명시적 테이블 락**

   **LOCK TABLES table_name \[ READ | WRITE \]** 명령으로 획득하고 **UNLOCK TABLES** 명령으로 잠금을 해제할 수 있다.

   다만 명시적 테이블 락은 `굳이 사용할 필요가 없다`. 글로벌 락 처럼 온라인 작업에 영향을 많이 미치기 때문이다.

2. **묵시적 테이블 락**

   **MyISAM 이나 MEMORY 테이블**의 데이터를 변경하는 쿼리를 실행하면 묵시적 테이블 락이 획득된다. 쿼리가 실행되는 동안 자동으로 획득되었다가 쿼리가 완료되면 자동으로 해제된다.

   **InnoDB 테이블**의 경우에는 데이터를 변경하는 `DML 쿼리에서는 테이블 락이 획득되지 않고`<br>
   `스키마를 변경하는 DDL 쿼리가 실행되는 경우 획득`된다. InnoDB 스토리지 엔진 차원에서 레코드 기반 잠금을 제공하기 때문에 단순 DML 로는 묵시적 테이블 락이 잡히지 않는 것이다.

## 네임드 락 (Named Lock)

> 💡 **네임드 락 (Named Lock)**
>
> - <strong>임의의 `문자열에 대한 잠금`</strong>이다.
> - 테이블이나 레코드, AUTO_INCREMENT 와 같은 데이터베이스 객체를 대상으로 한 잠금이 아니다.
> - 자주 사용되지는 않는다.

자주 사용되지는 않으나, 다음 두 가지 상황에 사용될 수 있다.

1. **여러 클라이언트가 특정 정보를 동기화 처리해야 하는 상황**
2. **배치 프로그램과 같이 많은 레코드에 대해 복잡한 요건으로 레코드를 변경하는 트랜잭션의 경우**

특히, 한꺼번에 많은 레코드를 변경하는 쿼리는 데드락의 원인이 되기 십상이다. 이러한 경우 **동일 데이터를 변경하거나 참조하는 프로그램끼리 분류**해 **네임드 락을 걸고 쿼리를 실행**하면 간단히 해결할 수 있다.

사용 예시를 간단히 보고 다음으로 넘어가도록 하자.

```sql
--// "mylock_1" 문자열에 대해 잠금 획득
--// 이미 잠금을 사용 중이면 10초 동안 대기 (10초 이후 잠금 자동 해제)
SELECT GET_LOCK('mylock_1', 10);

--// "mylock_1"에 대한 작업 실행
SELECT GET_LOCK('mylock_2', 10);

--// "mylock_1", "mylock_2"에 대한 작업 실행
SELECT RELEASE_LOCK('mylock_2');

SELECT RELEASE_LOCK('mylock_1');

--// mylock_1, mylock_2 을 동시에 해제
SELECT RELEASE_ALL_LOCKS();
```

## 메타데이터 락 (Metadata Lock)

> 💡 **데이터베이스 객체(테이블, 뷰 등)의 이름이나 구조를 변경하는 경우에 획득하는 잠금**<br>
> 메타데이터 락은 **명시적으로 획득하거나 해제하는 잠금이 아니다**.

**`RENAME TABLE tab_a TO tab_b`** 과 같이 **테이블의 이름을 변경하는 경우 자동으로 메타데이터 락을 획득**한다.

**`RENAME TABLE`** 명령은 '원본 이름'과 '변경될 이름' 두 개 모두 한꺼번에 잠금을 설정해야한다.

### 메타 데이터 락의 예시

배치 프로그램에서 임시 테이블 **rank_new** 에 서비스용 랭킹 데이터를 생성할 예정이다. 현재 서비스에 사용중인 테이블의 이름은 **rank** 이다.

임시 테이블 **rank_new** 에 랭킹 배치가 완료되면, 현재 사용중인 **rank** 테이블을 **rank_backup** 으로 백업하고 새로운 서비스용 랭킹 데이터가 담긴 **rank_new** 테이블을 서비스용으로 교체하고자 한다.

```sql
RENAME TABLE rank TO rank_backup;
RENAME TABLE rank_new TO rank;
```

1. **`RENAME TABLE`** 명령을 사용해 **rank** 테이블의 이름을 **rank_backup** 으로 바꾼다.
2. **`RENAME TABLE`** 명령을 사용해 **rank_new** 테이블의 이름을 **rank** 로 바꾼다.

흐름 상으로는 위의 1,2 번 순서에 따라 두 번의 **`RENAME TABLE`** 명령으로 문제를 해결할 수 있을 듯 하다.

하지만 가슴아프게도 위와 같이 실행하면 **`Table not found 'rank'`** 라는 오류를 만나게 될 가능성이 생긴다.

만약 1번이 실행되고 2번 명령이 실행되기 전에 **rank** 테이블에 대한 쿼리가 요청되면, 아주 짧은 시간이지만 **rank** 테이블이 존재하지 않는 순간이 생기기 때문이다.

따라서 아래와 같이 **`RENAME TABLE`** 명령문에 두 개의 **RENAME 작업을 한꺼번에 실행**시켜줘야 한다.

```sql
RENAME TABLE rank TO rank_backup, rank_new TO rank;
```

위의 경우와 다르게 메타데이터 락과 InnoDB 트랜잭션을 동시에 사용해야 하는 경우도 있다. 해당 내용은 관련 글에서 살펴보도록 하자.
