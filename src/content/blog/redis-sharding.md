[앞 글](/blog/redis-replication/)에서 본 것처럼 복제는 모든 노드가 같은 데이터를 가집니다. 서버를 늘려도 담을 수 있는 양은 마스터 한 대의 메모리를 넘지 못합니다.
데이터가 서버 한 대의 메모리를 넘으면 여러 서버에 나눠 담아야 합니다. 이것을 샤딩이라고 합니다.

예를 들어 100GB를 32GB 서버 4대에 25GB씩 나눠 담는다고 해 봅시다. 바로 두 가지를 정해야 합니다. 저장할 때 어느 서버에 넣을지, 읽을 때 그 키가 어느 서버에 있는지입니다.
[우아한레디스 발표](https://www.youtube.com/watch?v=mPB2CZiAkKM)의 표현을 빌리면 "데이터를 어떻게 나눌 것인가"는 곧 "데이터를 어떻게 찾을 것인가"입니다.

- **모듈러:** 서버 수로 나눈 나머지로 고릅니다. 서버 수가 바뀌면 대부분의 키가 움직입니다. 3대에서 4대로 늘리면 75%가 움직입니다.
- **범위:** 키 범위마다 서버를 정합니다. 새 데이터가 한 범위로 몰리는 쏠림이 약점입니다.
- **인덱스:** 키의 위치를 적어 둔 서버에 물어봅니다. 그 서버가 죽으면 전체가 멈춥니다.
- **일관된 해싱:** 서버 수가 바뀌어도 평균 1/N만 움직입니다. 가상 노드로 분포를 고르게 맞추고, 계산은 클라이언트 라이브러리나 프록시가 합니다.
- **해시 슬롯:** Redis Cluster의 방식입니다. 키를 16384개의 고정된 슬롯으로 나누고, 노드를 늘리거나 줄일 때는 슬롯 단위로 옮깁니다.

## 한눈에 보기

| 방식 | 키의 위치를 정하는 법 | 서버가 늘거나 줄 때 | 약점 |
| --- | --- | --- | --- |
| 모듈러 | `hash(key) % 서버 수` | 대부분의 키가 이동 | 증설 비용 |
| 범위 | 키 범위 표 | 범위를 다시 나눠야 함 | 쏠림 |
| 인덱스 | 인덱스 서버에 물어봄 | 인덱스만 고치면 됨 | 인덱스 서버가 단일 장애 지점 |
| 일관된 해싱 | 해시 링에서 시계 방향으로 처음 만나는 서버 | 평균 1/N만 이동 | 가상 노드가 필요, 서버 목록을 모든 클라이언트가 맞춰야 함 |
| 해시 슬롯 | `CRC16(key) mod 16384` → 슬롯 → 노드 | 옮기는 슬롯의 키만 이동 | 여러 키를 다루는 명령은 같은 슬롯에서만 |

## 모듈러 샤딩

키를 해시한 값(키가 정수면 그대로)을 서버 수 N으로 나눈 나머지로 서버를 고릅니다. 계산만으로 위치가 정해져서 따로 물어볼 곳이 필요 없고, 키가 고르게 퍼집니다.

문제는 서버 수가 바뀔 때입니다. 나누는 수가 바뀌면 거의 모든 키의 나머지가 바뀝니다.
3대에서 4대로 늘리면 `k % 3`과 `k % 4`가 같은 키만 제자리에 남습니다. 나머지는 12(3과 4의 최소공배수)마다 되풀이되는데, 0부터 11까지 중 두 나머지가 같은 수는 0, 1, 2 세 개뿐입니다. 키가 고르게 퍼져 있다면 75%가 다른 서버로 옮겨 가야 합니다. 일반적으로 N대에서 N+1대로 늘리면 N/(N+1)이 움직입니다.

발표에서는 이를 줄이려고 서버를 늘릴 때 두 배(N대 → 2N대)로 늘리는 방법을 소개합니다. `k % 2N`은 `k % N`과 같거나 그보다 N만큼 크므로, 각 서버의 데이터 중 절반만 새 서버로 옮기면 됩니다.
대신 늘릴 때마다 서버 수가 두 배가 되니 필요보다 많이 늘리게 됩니다.

Redis Cluster의 해시 슬롯도 나머지 연산을 씁니다. 다른 점은 나누는 수가 서버 수가 아니라 16384로 고정되어 있다는 것입니다. 키가 몇 번 슬롯에 들어가는지는 서버가 늘어도 바뀌지 않습니다.

## 범위 샤딩

키의 범위를 정해 두고 범위마다 서버를 정합니다. 예를 들어 회원 번호 1~1000은 A, 1001~2000은 B, 2001~3000은 C에 둡니다.

약점은 쏠림입니다. 새로 가입하는 회원은 모두 가장 최근 범위로 들어가니 그 서버만 바쁘고 나머지는 놉니다.
발표의 예처럼 이벤트 기간에 가입자가 한 범위에 몰렸다가 이벤트가 끝나고 한꺼번에 탈퇴하면, 그 범위를 맡은 서버는 텅 빕니다. 범위를 기준으로 담았기 때문에 바쁜 서버의 데이터를 한가한 서버로 나눠 옮기기도 어렵습니다.

Redis Cluster는 키를 해시해서 슬롯에 흩어 놓기 때문에 이런 쏠림이 덜합니다. 슬롯을 노드에 나눠 줄 때는 0~5500처럼 범위로 주지만, 어떤 키가 어느 슬롯에 들어가는지는 해시가 정합니다.

## 인덱스 샤딩

키가 어느 서버에 있는지 적어 둔 인덱스 서버(디렉터리)를 따로 둡니다. 저장하거나 읽기 전에 인덱스 서버에 물어보고, 데이터를 옮길 때는 인덱스만 고치면 됩니다. 원하는 대로 배치할 수 있어 유연합니다.

대신 인덱스 서버가 죽으면 무엇이 어디에 있는지 알 수 없어 서비스 전체가 멈춥니다. 요청마다 한 번 더 물어봐야 하는 비용도 붙습니다.

Redis Cluster에는 이런 중앙 서버가 없습니다. 모든 노드가 어느 슬롯을 누가 맡는지 알고 있고, 노드끼리 주고받는 하트비트(ping/pong)에 자기가 맡은 슬롯 목록을 비트맵으로 실어 보내 서로 맞춥니다. "100번 슬롯은 이제 내가 맡았다"를 소문내는 식입니다.
클라이언트도 슬롯 배치를 받아 두고 직접 계산하므로, 요청마다 누구에게 물어볼 필요가 없습니다.

## 일관된 해싱 (Consistent Hashing)

모듈러 방식에서 서버 수가 바뀔 때 대부분의 키가 움직이는 문제를 줄이려고 나온 방법입니다. 1997년 MIT의 Karger 등이 분산 웹 캐시를 위해 소개했습니다.

### 해시 링

해시 값의 범위를 원처럼 이어 붙인 것을 해시 링이라고 합니다(예: 0부터 2^32 - 1까지. 범위는 구현마다 다릅니다).

1. 서버를 해시해서 링 위에 올립니다.
2. 키도 해시해서 링 위에 올립니다.
3. 키는 링을 시계 방향으로 돌다가 처음 만나는 서버에 저장합니다.

서버를 하나 더하면, 새 서버와 반시계 방향으로 바로 앞 서버 사이에 있던 키만 새 서버로 옮겨 갑니다. 이 키들은 원래 새 서버의 시계 방향 다음 서버에 있던 키입니다.
서버가 빠지면 그 서버의 키만 시계 방향 다음 서버로 넘어갑니다. 키가 K개, 서버가 N대면 평균 K/N개만 움직입니다. 모듈러처럼 전체가 뒤섞이지 않습니다.

### 가상 노드

서버가 몇 대 안 되면 링 위의 위치가 운에 따라 한쪽으로 몰릴 수 있습니다(예: 12시, 1시, 2시 방향). 그러면 넓은 구간을 맡은 서버에 키가 몰립니다.
또 서버 하나가 빠지면 그 서버의 키가 전부 바로 다음 서버 한 대로 넘어가, 그 서버의 부하가 두 배 가까이 됩니다.

그래서 실제 서버 하나를 링 위 여러 곳에 올립니다. 이를 가상 노드(virtual node)라고 합니다.
서버 A를 A-1, A-2, …, A-100처럼 여러 점으로 흩어 두면 구간이 고르게 나뉘고, 서버 하나가 빠져도 그 키들이 여러 서버로 흩어집니다.

### 계산은 누가 하나

Redis 서버 자체는 일관된 해싱을 모릅니다. 계산은 클라이언트 라이브러리나 프록시가 합니다.

- **프록시:** Twitter가 만든 twemproxy는 기본 분배 방식이 일관된 해싱(ketama)입니다.
- **클라이언트:** 예전 Jedis의 샤딩 기능(`ShardedJedis`, 4.x부터 `JedisSharding`)이 이 방식이었습니다. 5.x 코드를 줄여 보면 이렇습니다.

```java
// 서버마다 가상 노드 160개를 MurmurHash로 링(TreeMap)에 올립니다.
for (int i = 0; i < shards.size(); i++) {
  for (int n = 0; n < 160; n++) {
    Long hash = algo.hash("SHARD-" + i + "-NODE-" + n);
    nodes.put(hash, shards.get(i));
  }
}

// 키의 해시 이상인 첫 노드를 고르고, 없으면 링의 처음으로 돌아갑니다.
SortedMap<Long, HostAndPort> tail = nodes.tailMap(hash);
return tail.isEmpty() ? nodes.get(nodes.firstKey()) : tail.get(tail.firstKey());
```

이 기능은 Jedis 7.0에서 제거되었고, 이관 가이드는 여러 대에 나눠 쓰려면 `JedisCluster`를 쓰라고 안내합니다.

일관된 해싱은 키를 서버에 대응시키는 규칙일 뿐입니다. 모든 클라이언트(또는 프록시)가 같은 서버 목록을 같은 순서로 알고 있어야 같은 키를 같은 서버에서 찾습니다. 위 코드에서도 서버의 순번 `i`가 가상 노드의 해시에 들어갑니다.
서버를 더하거나 뺄 때 옮겨야 할 키를 실제로 옮기는 일도 해 주지 않습니다. 캐시라면 옮기지 않고, 새 서버에서 캐시 미스를 한 번 겪고 다시 채우는 것으로 넘어가기도 합니다.

## 해시 슬롯: Redis Cluster의 방식

Redis 공식 문서는 Redis Cluster가 일관된 해싱을 쓰지 않고, 모든 키가 해시 슬롯에 속하는 다른 형태의 샤딩을 쓴다고 설명합니다.

### 키에서 슬롯, 슬롯에서 노드

```text
HASH_SLOT = CRC16(key) mod 16384
```

- 슬롯은 0부터 16383까지 16,384개로 고정입니다. CRC16(XMODEM)의 16비트 중 14비트만 쓰는 셈이라, 구현에서는 `& 16383`으로 계산합니다.
- 마스터 노드마다 슬롯 일부를 맡습니다. 공식 문서의 예로 노드가 셋이면 A가 0~5500, B가 5501~11000, C가 11001~16383을 맡습니다.
- 키는 노드가 아니라 슬롯에 대응됩니다. 어떤 키가 몇 번 슬롯인지는 `CLUSTER KEYSLOT <key>`로 확인할 수 있습니다.

| 키 | 슬롯 | 위 예에서 맡는 노드 |
| --- | --- | --- |
| `bar` | 5061 | A (0~5500) |
| `somekey` | 11058 | C (11001~16383) |
| `{user1000}.following` | 3443 | A |
| `{user1000}.followers` | 3443 | A |

아래 두 키가 같은 슬롯인 이유는 뒤의 해시 태그에서 설명합니다.

### 노드를 늘리고 줄일 때

노드 D를 더하려면 A, B, C가 맡던 슬롯을 조금씩 떼어 D에 넘깁니다. A를 빼려면 A의 슬롯을 B와 C로 옮긴 뒤 비워진 A를 빼면 됩니다.
옮기는 단위가 슬롯이라 옮기는 슬롯에 속한 키만 움직이고, 나머지 키의 위치는 그대로입니다. 서비스를 멈추지 않고 할 수 있습니다.

A의 8번 슬롯을 B로 옮기는 과정은 이렇습니다.

1. B에는 8번 슬롯을 `IMPORTING`으로, A에는 `MIGRATING`으로 표시합니다.
2. A는 8번 슬롯의 키 중 자기에게 있는 키는 직접 처리하고, 없는 키는 `-ASK`로 B에 보냅니다. 그래서 이 슬롯의 새 키는 A에 생기지 않습니다.
3. `redis-cli`가 `CLUSTER GETKEYSINSLOT`으로 키를 꺼내 `MIGRATE`로 B에 옮깁니다. 키를 옮기는 짧은 동안 두 노드가 잠겨서, 클라이언트 입장에서 키는 언제나 A와 B 중 한 곳에만 있습니다.
4. 다 옮기면 `CLUSTER SETSLOT 8 NODE <B의 ID>`로 소유를 확정합니다.

원소가 아주 많은 큰 키는 `MIGRATE`에 오래 걸립니다. 공식 문서는 지연에 민감한 서비스라면 큰 키가 있는 상태에서 리샤딩하는 것은 좋은 생각이 아니라고 적고 있습니다.
Redis 8.4에는 슬롯 단위로 원자적으로 옮기는 `CLUSTER MIGRATION` 명령이 들어왔고, 8.10부터는 `redis-cli --cluster reshard`와 `rebalance`가 이 방식으로 슬롯을 옮깁니다.

### 클라이언트는 어떻게 찾아가나

클러스터 노드는 요청을 다른 노드로 대신 전달하지 않습니다. 대신 잘못 온 요청에 올바른 노드를 알려 줍니다.

- **`-MOVED 3999 127.0.0.1:6381`:** 이 슬롯은 저 노드가 맡는다는 뜻입니다. 클라이언트는 그 노드로 다시 보내고, 자기가 들고 있는 슬롯 배치를 고칩니다. 슬롯 여러 개가 한꺼번에 바뀌었을 가능성이 높아서, 공식 문서는 이때 `CLUSTER SHARDS`로 배치 전체를 다시 받아 오는 방법도 권합니다.
- **`-ASK`:** 슬롯을 옮기는 중이니 이번 요청만 저 노드로 보내라는 뜻입니다. 클라이언트는 그 노드에 `ASKING`을 먼저 보낸 뒤 요청을 보내고, 슬롯 배치는 고치지 않습니다.

그래서 클러스터를 쓰려면 이 두 리다이렉션을 처리하는 클러스터 지원 클라이언트가 필요합니다. 클라이언트가 슬롯 배치를 들고 있으면, 배치가 바뀌지 않는 동안에는 모든 요청이 리다이렉션 없이 한 번에 맞는 노드로 갑니다.

### 여러 키를 다루는 명령과 해시 태그

여러 키를 다루는 명령은 트랜잭션과 Lua 스크립트를 포함해 모든 키가 같은 슬롯에 있을 때만 실행됩니다. 슬롯이 다르면 `CROSSSLOT` 오류가 납니다.
함께 다뤄야 하는 키를 같은 슬롯에 두려면 해시 태그를 씁니다. 키에 `{...}`가 있으면 중괄호 안의 문자열만 해시합니다.

- 첫 `{`가 있고, 그 오른쪽에 `}`가 있고, 둘 사이에 한 글자 이상 있으면 그 사이만 해시합니다.
- `{user1000}.following`과 `{user1000}.followers`는 `user1000`만 해시하므로 같은 슬롯(3443)입니다.
- `foo{}{bar}`는 첫 `{` 바로 뒤가 `}`라서 키 전체를 해시합니다.
- `foo{bar}{zap}`은 첫 짝인 `bar`만 해시해서 `bar`와 같은 5061번 슬롯입니다.

해시 태그로 너무 많은 키를 한 슬롯에 몰면 그 슬롯을 맡은 노드만 바빠집니다. 함께 다뤄야 하는 키끼리만 묶는 것이 좋습니다.

### 왜 16384개인가

Redis를 만든 antirez가 [GitHub 이슈](https://github.com/redis/redis/issues/2576)에서 설명한 이유는 두 가지입니다.

1. 노드끼리 주고받는 하트비트에는 자기가 맡은 슬롯 목록이 비트맵 그대로 들어갑니다. 슬롯이 16384개면 2KB지만, 65536개면 8KB가 되어 너무 큽니다.
2. 다른 설계상의 이유로 Redis Cluster가 마스터 1000대를 넘을 일은 드뭅니다. 16384개면 마스터가 1000대여도 한 대당 슬롯이 충분합니다.

그래서 이론상 최대 마스터 수는 16384대지만, 공식 문서가 권하는 규모는 1000대 정도입니다.

### 일관된 해싱과 무엇이 다른가

- **옮기는 단위:** 해시 슬롯은 슬롯으로 고정입니다. 몇 번 슬롯을 누가 맡는지만 바뀌고, 키가 몇 번 슬롯인지는 바뀌지 않습니다.
- **배치를 누가 관리하나:** 일관된 해싱은 클라이언트마다 같은 서버 목록으로 링을 계산해야 합니다. 클러스터는 노드들이 슬롯 배치를 관리하고, 배치가 엇갈리면 설정 버전(epoch)이 큰 쪽을 따릅니다. 클라이언트는 틀려도 `MOVED`로 바로잡힙니다.
- **제약:** 여러 키를 다루는 명령은 같은 슬롯에서만 됩니다. 데이터베이스는 0번만 쓸 수 있어 `SELECT`를 못 씁니다. 클러스터를 지원하는 클라이언트가 필요합니다.

## 정리

- 모듈러는 계산이 단순하지만 서버 수가 바뀌면 대부분의 키가 움직입니다. 범위는 쏠림을, 인덱스는 인덱스 서버라는 단일 장애 지점을 떠안습니다.
- 일관된 해싱은 서버 수가 바뀔 때 움직이는 키를 평균 1/N로 줄입니다. 계산은 클라이언트나 프록시가 하고, 데이터를 옮기는 일은 따로 해야 합니다.
- Redis Cluster는 키를 16384개 슬롯에 고정해 두고 슬롯 단위로 옮깁니다. 슬롯 배치는 노드들이 관리하고, 클라이언트는 `MOVED`와 `ASK`로 따라갑니다.
- 샤딩은 용량을 늘려 주지만 가용성은 따로입니다. 공식 문서의 예처럼 노드 B가 죽으면 5501~11000번 슬롯을 맡을 노드가 없어 클러스터가 계속 동작할 수 없습니다. 노드마다 레플리카를 두고 장애 때 올리는 방법은 [다음 글](/blog/redis-high-availability/)에서 다룹니다.
