먼저 위 그림을 천천히 살펴보자.

### 1. 프로그래밍 API

> 💡 MySQL은 대부분의 프로그래밍 언어에서 사용할 수 있는 드라이버를 제공한다. 대표적으로 Java 에서 사용하는 JDBC가 있다.<br>
> 이외에도 ODBC, PHP MySQL 드라이버, .NET MySQL 드라이버 등이 있다.

이러한 드라이버를 이용해 자바, C/C++, PHP, 파이썬, 루비 등 모든 언어로 MySQL 서버에서 쿼리를 사용할 수 있도록 지원한다.

### 2. MySQL 엔진

> 💡 MySQL 엔진은 클라이언트의 접속 및 쿼리 요청을 처리하고, 요청된 SQL 문장을 분석하고 최적화 하는 등 DBMS 의 두뇌에 해당하는 작업을 수행한다.

- **커넥션 핸들러**
  - 클라이언트로부터의 접속 및 쿼리 요청을 처리
- **SQL 파서 및 전처리기**
  - **SQL 파서**는 사용자의 요청으로 들어온 쿼리 문장을 토큰 단위로 분리해 트리 형태의 구조로 만들어낸다. 쿼리 문장의 기본 문법 검증이 이 단계에서 이루어지고, 사용자에게 오류 메시지를 전달한다.
  - **전처리기**는 파싱(parsing) 과정에서 만들어진 파서(parser) 트리를 기반으로 쿼리 문장에 구조적 문제가 있는지 확인한다. 각 토큰을 테이블 이름, 컬럼 이름 등과 같은 개체로 매핑해, 해당 객체의 존재 여부와 접근 권한 등을 확인하는 과정을 수행한다.
- **SQL 옵티마이저**
  - 사용자의 요청으로 들어온 쿼리 문장을 저렴한 비용으로 가장 빠르게 처리할 수 있는 방법을 선택한다.

### 3. 스토리지 엔진

> 💡 스토리지 엔진은 실제 데이터를 **디스크 스토리지에 저장**하고,<br>
> **디스크 스토리지로부터 데이터를 읽어오는 작업을 수행**

MySQL 서버에서 MySQL 엔진은 하나지만, **`스토리지 엔진은 여러 개를 동시에 사용할 수 있다`**.

다음 예제와 같이 테이블이 사용할 스토리지 엔진을 지정해 줄 수 있다.

```sql
CREATE TABLE test_table (fd1 INT, fd2 INT) ENGINE=INNODB;
```

`test_table` 은 이제 `InnoDB` 스토리지 엔진을 사용해 모든 읽기 쓰기 등의 작업을 처리할 것이다.

### 여기까지. 궁금한 점이 생긴다.

분명 MySQL 엔진에서 사용자 요청을 받아 쿼리 문장을 분석/검증 하고 최적화 작업을 수행하고,<br>
스토리지 엔진이 그 실제 데이터를 디스크 스토리지에 저장하거나 읽는 작업을 수행한다고 했다.

이렇게 기능이 철저히 분리되어 있다면, MySQL 엔진과 스토리지 엔진의 소통은 불가피하다. 그렇다면 어떤 방식으로 MySQL 서버의 두 엔진이 소통을 하는 것일까?

그 답은 **`핸들러 API`** 에 있다.

### 핸들러 API

> 💡 MySQL 엔진의 쿼리 실행기에서 데이터를 읽고 쓸 때 **핸들러 API 를 통해서** 각 스토리지 엔진에 읽기 또는 쓰기 작업을 요청한다.

default 스토리지 엔진인 InnoDB 스토리지 엔진 또한 이 핸들러 API 를 이용해 MySQL 엔진과 데이터를 주고받는다.

> 📌 **주의**
>
> MySQL 에서 핸들러는 개념적인 내용이므로 완전히 이해하지 못해도 문제가 되진 않는다.<br>
> 다만 다음 두 가지 사항은 기억해두자.
>
> 1. **MySQL 엔진이 각 스토리지 엔진에게 데이터를 읽어오거나 저장하도록 명령하려면 반드시 핸들러를 통해야 한다.**
> 2. **`대부분의 작업이 MySQL 엔진에서 처리`되고 `마지막 데이터 읽기 쓰기 작업만 스토리지 엔진에서 처리`된다.**
>
> ```sql
> SHOW GLOBAL STATUS LIKE 'Handler%';
> ```

## MySQL 스레딩 아키텍처

<figure>
<img src="/images/mysql-architecture/02.png" alt="MySQL 스레딩 모델 - 출처 [Real MySQL 8.0 1권]" width="1320" height="810" loading="lazy" decoding="async" />
<figcaption>MySQL 스레딩 모델 - 출처 [Real MySQL 8.0 1권]</figcaption>
</figure>

1. MySQL 서버는 프로세스 기반이 아니라 스레드 기반으로 동작. (**포그라운드 스레드**와 **백그라운드 스레드**)
2. MySQL 엔터프라이즈 에디션에서는 전통적인 스레드 모델뿐 아니라 **스레드 풀 모델**을 사용할 수도 있음.

`전통적인 스레드 모델`에서는 **커넥션 별로 포그라운드 스레드가 하나씩 생성되고 할당**된다.

`스레드 풀 모델`에서는 커넥션과 포그라운드 스레드가 1:1 관계를 이루지 않고, **하나의 스레드가 여러 개의 커넥션 요청을 전담**한다.

### 1. 포그라운드 쓰레드 (클라이언트 쓰레드)

> 클라이언트가 MySQL 서버에 접속<br>
> → **스레드를 생성해 그 클라이언트에게 할당**
>
> → **포그라운드 스레드(사용자 스레드)**

- **포그라운드 스레드**는 **MySQL 서버에 접속된 클라이언트의 수만큼 존재**
- 각 클라이언트 사용자가 요청하는 **`쿼리 문장을 처리`**
- 커넥션을 종료 시, 해당 커넥션을 담당하던 쓰레드는 쓰레드 캐시로 반납
  - 쓰레드 캐시에 대기중인 쓰레드가 일정 개수 이상 존재하면, 쓰레드 캐시에 넣지 않고 쓰레드를 종료시킴
  - 최대 스레드 개수는 **`thread_cache_size`** 시스템 변수로 설정

### 2. 백그라운드 쓰레드

백그라운드  쓰레드는 **데이터의 쓰기 작업을 수행**한다.

InnoDB 에서는 다양한 작업들을 백그라운드 스레드에서 처리한다.

- **로그 스레드(Log thread)** : 로그를 디스크로 기록하는 작업을 처리
- **쓰기 스레드(Write thread)** :  버퍼의 데이터를 디스크로 쓰는 작업을 처리
  - 일반적인 내장 디스크를 사용할 때는 2~4 정도로 설정

> 📌 **`읽기 = 클라이언트 쓰레드`, `쓰기 = 백그라운드 쓰레드` 인 이유**
>
> InnoDB 에서 **데이터를 읽는 작업은 주로 클라이언트 스레드가 처리**하기 때문에 읽기 스레드는 많이 설정할 필요가 없다.
>
> 사용자의 요청을 처리하는 **도중 데이터의 쓰기 작업은 지연(버퍼링)되어 처리할 수 있지만, 데이터의 읽기 작업은 절대 지연될 수 없기 때문**이다.
>
> `SELECT` 쿼리를 날렸는데 요청이 지연되어 10분 뒤에 결과를 보내주는 DBMS 가 있다면 이미 망하고 사라져버렸을 것이다.
>
> 따라서 InnoDB 에서는 `INSERT`, `UPDATE`, `DELETE` 쿼리로 **데이터가 변경되는 경우 데이터가 디스크의 데이터 파일로 완전히 저장될 때 까지 기다리지 않아도 되는 것**이다.

## MySQL 의 메모리 구조

<figcaption>MySQL 메모리 구조</figcaption>
</figure>

### 1. 글로벌 메모리 영역

> **클라이언트 스레드 수와 무관하게 하나의 메모리 공간만 할당**되고 **모든 스레드에 의해 공유되는 영역**이다.

대표적인 글로벌 메모리 영역은 다음과 같다.

- 테이블 캐시
- InnoDB 버퍼 풀
- InnoDB 어댑티브 해시 인덱스
- InnoDB 리두 로그 버퍼

### 2. 로컬 메모리 영역

> 클라이언트 스레드가 쿼리를 처리하는 데 사용하는 메모리 영역이다.

대표적인 로컬 메모리 영역은 다음과 같다.

- 정렬 버퍼
- 조인 버퍼
- 네트워크 버퍼
- 바이너리 로그 캐시

**정렬 버퍼 / 소트 버퍼** 의 경우 쿼리 용도별로 필요할 때만 메모리 공간을 할당받고 필요하지 않은 경우 아예 할당받지 않을 수도 있다.

즉, **쿼리를 실행하는 순간에만 메모리 공간을 할당받고 다시 해제**한다.

이와는 반대로 **커넥션 버퍼 / 결과 버퍼** 의 경우 커넥션이 열려 있는 동안 계속 할당된 상태로 남아있는다.

## 요약

- **MySQL 서버는 MySQL 엔진과 스토리지 엔진으로 나눌 수 있다.**
- **스토리지 엔진은 핸들러 API 를 만족하면 누구든 추가해 사용할 수 있다.**
- **대부분의 작업이 MySQL 엔진에서 처리되고 마지막 데이터 읽기 쓰기 작업만 스토리지 엔진에서 처리된다.**
