레포가 다섯 개입니다. 백엔드, 파이프라인, 지식 도구, 웹, 어드민. 세션을 열 때마다 같은 설명을
다시 했습니다. 레이어 규칙은 이렇고, 이 테이블은 저렇고, 이건 건드리면 안 되고.

한동안은 프롬프트를 더 잘 쓰면 해결될 문제라고 생각했습니다. 아니었습니다.
**지침이 없어서가 아니라, 써 놓은 지침이 읽히지 않는 위치에 있었습니다.**

정리하면서 원칙을 네 줄로 고정했습니다. 이 글은 그 네 줄을 실제로 세우는 과정입니다.

> 지침은 단일 원천에, 규칙은 버전 관리되는 위치에,
> 위험한 행동은 기계적으로 막고, **측정하지 않은 것은 주장하지 않는다.**

세우고 나니 한 바퀴가 이렇게 돌게 됐습니다. 에이전트가 지침을 읽고 일하면(01),
게이트가 기계적으로 걸러내고(02), 걸린 것은 사람에게 넘어오고(EX),
사람이 판단한 뒤(04) 출시하고 같은 지표로 다시 재는(05) 순환입니다.

## 1단계. "한 곳에 모은다"가 생각보다 어렵다

파일을 루트에 모으면 끝날 줄 알았습니다. 그런데 하위 레포에서 세션을 열면 skill이 안 보였습니다.
지침은 읽히는데 skill만 사라졌습니다.

공식 문서를 확인하고 나서야 이유를 알았습니다. **메커니즘마다 탐색 범위가 전부 다릅니다.**

| 대상 | 탐색 범위 | 그래서 어디에 뒀나 |
| --- | --- | --- |
| `CLAUDE.md` | cwd에서 `/`까지 **모든 상위 디렉터리** (git 경계 무관) | 워크스페이스 루트에 하나 |
| skill | cwd에서 **git 루트까지만** + `~/.claude/skills` | `~/.claude/skills`에 심볼릭 링크 |
| `settings.json` / hook | **상속 없음.** cwd와 `~/.claude`만 | `~/.claude/settings.json` |
| `AGENTS.md` | 상위 어디에도 `CLAUDE.md`가 없을 때만 읽음 | `CLAUDE.md`에서 `@AGENTS.md`로 가져옴 |

`CLAUDE.md`는 git 경계를 무시하고 루트까지 올라갑니다. 그래서 워크스페이스 루트에 하나만 두면
모든 하위 레포 세션이 공통 컨텍스트를 받습니다.

skill은 다릅니다. **git 루트에서 멈춥니다.** 하위 레포는 그 자체가 git 저장소라서,
워크스페이스 루트의 `.claude/skills/`까지 올라가질 못합니다. 원본은 루트에 두고
`~/.claude/skills`로 링크를 걸어 해결했습니다. 버전 관리는 루트에서 하고,
탐색은 홈에서 되게 한 겁니다.

`settings.json`과 hook은 상속이 아예 없습니다. 상위 디렉터리를 보지 않습니다.
그래서 가드는 선택의 여지 없이 `~/.claude`로 갔습니다. **이게 나중에 가장 큰 구멍이 됩니다.**

`AGENTS.md`는 작업 디렉터리와 그 위 어디에도 `CLAUDE.md`가 없을 때만 읽습니다. 루트에 `CLAUDE.md`를 둔
이 구성에서는 하위 레포의 `AGENTS.md`가 읽히지 않으니, 이미 써 둔 게 있다면 `CLAUDE.md`에서 `@AGENTS.md`로
가져와야 합니다.

> 같은 디렉터리에 나란히 둬도 하나는 읽히고 하나는 안 읽힙니다.
> 파일을 어디에 두느냐가 지켜지느냐를 정합니다.

## 2단계. 위험한 건 기계가 막는다

"이건 하지 마세요"를 지침에 쓰는 것으로는 부족했습니다. 지침은 읽고 잊히지만,
권한 규칙은 잊히지 않습니다.

권한은 **deny → ask → allow 순으로 평가되고 deny가 항상 이깁니다.**
기존에 편하려고 열어 둔 allow부터 걷어내고 deny를 채웠습니다.

| 판정 | 명령 | 이유 |
| --- | --- | --- |
| **deny** | 운영 인스턴스 원격 명령, pem 키 직접 SSH, 인프라 변경 명령, PR 머지, 운영 DB 재부팅·변경, 오토스케일링 용량 변경, 이미 머지된 마이그레이션 파일 수정 | 사람이 직접 한다 |
| **ask** | `git push`, 운영 세션 접속, 컨테이너 재시작·종료, 과금·실네트워크 테스트, 운영 DB 접속 | 되돌리기 어렵거나 운영에 닿는다 |
| **allow** | 그 외 (읽기·빌드·기본 테스트) | — |

기준은 "위험한가"가 아니라 **"되돌릴 수 있는가"와 "사람이 봐야 하는가"** 입니다.
PR 머지가 deny인 건 위험해서가 아니라 머지는 사람이 누르는 행위라고 봐서입니다.

판정 로직은 별도 스크립트로 빼서 단독 실행이 되게 했습니다. stdin에 샘플을 넣고
기댓값과 비교하는 테스트를 20건 돌렸고, 그 과정에서 과금 테스트 패턴 하나가 틀린 걸 잡았습니다.

### 가드는 실제로 맞아 봐야 안다

테스트가 통과해도 진짜 세션에서 hook이 발화하는지는 별개입니다.
스크립트에 센티널 문자열을 심고 아무 명령이나 하나 실행한 뒤 파일을 확인했습니다. 찍혔습니다.

그다음 진짜로 막힐 명령을 쳐 봤습니다. 차단됐고, 「운영 인스턴스 원격 명령은 사람이 직접 실행한다」는
사유가 돌아왔고, 명령은 실행되지 않았습니다.

> 문서로만 확인한 가드는 가드가 아닙니다.

### 솔직하게 적어 둔 한계

입력 파싱에 실패하면 **fail-open** 입니다. 통과시킵니다.
이건 마지막 방어선이 아니라 실수 방지선이라고 문서에 적어 뒀습니다.

그리고 이 가드는 **AI 세션 안에서만** 작동합니다. 제가 터미널에서 직접 치는 명령은 안 막습니다.
가드를 세워 놓고 "이제 안전하다"고 생각하는 게 제일 위험해서, 범위를 먼저 못 박았습니다.

## 3단계. 지침 파일 자체가 틀려 있었다

가드까지 세우고 나서, 지침에 써 놓은 구조 설명이 지금도 맞는지 확인해 봤습니다.
백엔드 지침에 있던 구조적 주장 다섯 건을 코드에 grep으로 하나씩 대조했습니다.

네 건은 맞았습니다. 한 건이 틀렸습니다.

**"어댑터 7개"라고 써 있었는데, 실제로는 어댑터 6개에 호출 지점이 7곳이었습니다.**

숫자 하나 차이지만 성격이 다릅니다. AI는 그 파일을 **사실로 읽습니다.**
틀린 전제가 들어가면 틀린 전제 위에서 코드를 씁니다. 그리고 지침 파일은 코드와 달리
CI가 검사해 주지 않습니다. 한 번 틀리면 조용히 계속 틀립니다.

그래서 규칙을 하나 더 만들었습니다. **지침에 쓰는 구조적 주장은 코드로 재확인한 것만 쓴다.**

같은 맥락에서 자체 리뷰 게이트도 실제 코드에 돌려 봤습니다. 오탐이 3건 나왔습니다 —
테스트 픽스처의 더미 시크릿, 외부 서비스 이름에 우연히 들어간 키워드, 발행 용도의 HTTP 클라이언트.
패턴을 정제해 0건으로 만들었습니다.

> 게이트를 만들고 "PASS"를 확인하는 것과, 게이트를 실코드에 돌려 **오탐을 걷어내는 것**은
> 다른 작업입니다. 후자를 안 하면 곧 게이트를 무시하기 시작합니다.

## 겪은 함정 네 가지

설계보다 함정이 더 많은 걸 가르쳐 줬습니다.

### 함정 ①. `git status`는 "머지됐는지"를 모른다

하위 레포의 규칙 파일들이 `git status`에 미추적(`??`)으로 떴습니다.
안 올라갔구나 싶어 커밋을 두 개 만들었습니다. 그런데 이미 올라가 있었습니다.

원인은 **로컬 브랜치가 기준 브랜치보다 뒤처져 있던 것**이었습니다.
기준 브랜치에 머지된 파일인데, 로컬이 2커밋 뒤라 로컬 시점에선 존재하지 않는 파일로 보였습니다.
fast-forward 하니 차이가 없었습니다. 중복 커밋 두 개는 되돌렸습니다.

확인은 `git status`가 아니라 기준 브랜치를 직접 봐야 합니다.

```bash
git ls-tree origin/<base> -- path/to/file
```

### 함정 ②. 검증 도구가 조용히 PASS를 낸다

이게 제일 무서웠습니다.

리뷰 게이트는 기준 브랜치와의 diff에 grep을 겁니다. 그런데 `$BASE`가 **존재하지 않는 참조**면
(원격을 fetch 안 한 상태 등) diff가 비고, grep은 0건을 돌려주고, 게이트는 **PASS로 보입니다.**

실제로 한 게이트가 그렇게 "0"으로 보인 적이 있었습니다.

> **0건은 "위반 없음"과 "검사 안 됨"을 구분하지 못합니다.**

검증 도구의 침묵을 통과로 읽는 건 가장 위험한 실패 모드입니다.
게이트 맨 앞에 참조 존재 검사를 넣었습니다.

```bash
git rev-parse --verify "$BASE" >/dev/null || exit 1
```

### 함정 ③. 사라진 worktree가 브랜치를 잡고 있다

머지 후 브랜치를 체크아웃하려는데 「already used by worktree」로 실패했습니다.
worktree 같은 걸 만든 기억이 없었습니다.

다른 세션이 임시 디렉터리에 만든 worktree였습니다. **디렉터리는 사라졌는데 git 메타데이터에만
남아(`prunable`) 브랜치를 잡고 있었습니다.** `git worktree prune`으로 네 개를 정리하니 풀렸습니다.

임시 디렉터리에 worktree를 만드는 세션은 끝낼 때 `git worktree remove`까지 해야 합니다.
안 그러면 다음 사람의 체크아웃이 막힙니다.

### 함정 ④. 가드가 자기 세션을 오탐한다

작업 중에 제 명령 두 개가 가드에 막혔습니다. 명령 본문에 차단 대상 문자열이
**설명으로** 들어가 있었기 때문입니다. 실행하려던 게 아니라 문서에 적으려던 것이었습니다.

오탐입니다. 다만 fail-closed 방향의 오탐이라 그대로 뒀습니다.
가드를 끄거나 우회하지 않고, 다른 도구를 쓰거나 문자열을 나눠서 처리했습니다.

> **오탐이 났을 때 가드를 끄는 순간, 그 가드는 없는 것입니다.**

덧붙이면 — 이 글을 쓰는 동안 같은 일이 한 번 더 났습니다.
위 deny 표를 파일로 저장하려는데 표 안의 인프라 명령 문자열에 가드가 걸렸습니다.
가드를 끄지 않고 다른 도구로 저장했습니다. 규칙은 이럴 때 지키라고 있는 겁니다.

## 4단계. 사다리 — 과잉 구현을 막는 장치

가드는 "위험한 행동"을 막습니다. 그런데 실제로 더 자주 일어나는 문제는 따로 있었습니다.
**안 쓸 것을 미리 만드는 것.** 인터페이스를 하나 더 파고, 공용 패키지를 신설하고,
"나중을 위해" 추상화를 얹는 일입니다.

이건 실재하는 병인데 막는 장치가 없었습니다. 외부 룰셋(MIT)을 가져오기로 했습니다.

플러그인으로 설치할 수 있었지만 **규칙 19줄을 직접 복사해 넣는(vendoring)** 쪽을 택했습니다.
플러그인은 자동 갱신됩니다. 규칙이 저장소 밖에서 바뀐다는 뜻입니다.
「규칙은 버전 관리되는 위치에」라는 원칙과 정면으로 충돌합니다.

네 단계로 넣었습니다.

### 0단계. 먼저 컨텍스트를 줄였다

규칙을 더하기 전에 뺐습니다. 파이프라인 레포의 지침이 25,595바이트까지 불어 있었습니다.

두 덩어리를 밖으로 뺐습니다. 자주 바뀌는 「현재 초점」은 상태 문서로, 문서 목록은 인덱스 파일로.
**8,696바이트로 66% 줄었습니다.**

중요한 건 그다음입니다. 줄였다고 주장하려면 **버린 게 아니라 옮긴 것**임을 보여야 합니다.
원본 174줄이 새 파일 셋 어딘가에 있는지 기계적으로 대조했습니다.
못 찾은 줄은 4줄이었고, 전부 절 제목과 안내 문구였습니다.

### 1~3단계. 규칙, 게이트, 장부

| 단계 | 한 일 |
| --- | --- |
| 1 | 루트 지침에 「코드를 쓰기 전 — 사다리」 7단 + 규칙 4 + **예외 3** |
| 2 | 리뷰 게이트에 과잉 구현 항목 추가 (새 외부 의존성 · 새 인터페이스 · 공용 패키지 신설 · "나중을 위한" 흔적) |
| 3 | 이미 알고 있던 한계 지점에 마커 주석을 달아 장부화 |

**예외 3이 핵심입니다.** 아키텍처 포트, 테스트 규약, 보고 규약은 사다리보다 우선한다고 못 박았습니다.
안 그러면 "간단하게 하라"가 "포트 생략해도 된다"로 번집니다.
단순화 규칙은 반드시 **무엇을 단순화하면 안 되는지**와 같이 와야 합니다.

2단계 게이트도 최근 커밋 25개에 먼저 돌려 오탐 세 종류를 걷어냈습니다 —
내부 모듈 참조, 아키텍처상 정당한 포트 인터페이스, 산문에 쓰인 "나중에".

## 결과 — 측정한 것과 측정하지 않은 것

### 측정한 것: 세션당 컨텍스트

| 세션 | 도입 후 | 비고 |
| --- | --- | --- |
| 백엔드 | 16.6KB | 루트 8.3 + 레포 3.6 + 레이어 규칙 4.7 |
| 파이프라인 | 17.0KB | 도입 전 **32KB** |

파이프라인 세션이 절반 가까이 줄었습니다. 이건 바이트 수라 그냥 재면 됩니다.

### 측정하지 않은 것: 효과

최근 머지된 PR을 레포당 5개씩 뽑아 변경 규모와 설명 길이를 기준선으로 떠 뒀습니다.
**다만 이걸 성과라고 쓰지 않기로 했습니다.**

n=5이고, 작업 성격이 서로 전혀 다릅니다. 어떤 PR은 194파일짜리 대규모 리팩터링이고
어떤 건 2파일짜리 수정입니다. 여기서 평균을 내 "줄었다"고 말하는 건 숫자를 빌린 인상평입니다.

수치 목표를 두지 않았습니다. 대신 관찰할 신호를 정성적으로 적었습니다.

> **만들고 안 쓰는 것이 새로 생기지 않는가.**

2주 뒤 같은 표를 다시 채워 결론을 적기로 했고, 되돌리기 조건도 미리 정했습니다 —
사다리 때문에 필요한 검증이나 포트가 빠진 사례가 **1건이라도** 나오면 즉시 예외 문구를 강화합니다.

이게 원칙의 마지막 줄입니다. 측정하지 않은 것은 주장하지 않습니다.

## 남은 구멍

### 가장 큰 것: 가드 설정이 버전 관리 밖에 있다

hook과 deny 규칙은 `~/.claude/settings.json`에 있습니다. 1단계에서 봤듯 상속이 없어서
거기 말고는 둘 데가 없습니다. **그런데 홈 디렉터리는 어느 저장소에도 안 들어갑니다.**

그 파일이 사라지면 deny 다섯 개와 hook 연결이 같이 사라집니다.
그리고 이게 진짜 문제인데 — **세션은 완전히 정상으로 보입니다.**
가드가 없어진 걸 알아챌 방법이 없습니다.

완화책으로 가드 부분만 떼어 `settings.json.example`로 저장소에 추적하고,
복원 명령과 검증 명령을 문서에 적어 뒀습니다.

```bash
jq -e '.permissions.deny | length' ~/.claude/settings.json   # 5가 나와야 한다
```

완전한 해결은 아닙니다. 파일이 사라진 걸 **먼저 알아채는** 장치가 여전히 없고,
hook 경로가 절대 경로라 다른 기기에 클론하면 손봐야 합니다.

### 나머지

- **세션 밖은 안 막습니다.** 제가 터미널에서 직접 치는 명령에는 가드가 없습니다.
- **일부 레포엔 지침이 없습니다.** 프론트 쪽은 자동 생성 블록뿐입니다. 필요해지면 넣기로 했습니다.
- **수정 후 자동 린트(PostToolUse)는 일부러 안 넣었습니다.** 느린 hook은 매 작업마다 비용을 물립니다.
  실수 방지 가치보다 비싸다고 판단했습니다. 필요해지면 CI에서 잡습니다.
- **루트 저장소에 원격이 없습니다.** 로컬 전용이라 기기가 죽으면 같이 죽습니다.

## 한 줄 요약

**나머지 절반은 그 지침이 지금도 사실인지 확인하는 일이었습니다.**

## 남은 생각

가장 오래 남은 건 함정 ②입니다. 검증 도구가 조용히 PASS를 내던 것.

가드를 세우고 게이트를 만들면 안심하게 됩니다. 그런데 그 장치들도 결국 코드고,
코드는 조용히 고장납니다. **"통과했다"와 "검사하지 않았다"가 같은 화면으로 보이는 순간**
그 장치는 안심만 주고 보호는 안 하는 물건이 됩니다.

그래서 다음에 게이트를 하나 더 만든다면, 먼저 물어볼 생각입니다 —
이게 고장 났을 때, 나는 어떻게 알게 되는가.
